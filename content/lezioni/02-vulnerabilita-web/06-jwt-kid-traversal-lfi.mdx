## Il filo

<Filo>Il sistema si fida di qualcosa che il client controlla. Se lo scrivi tu, non è una prova.</Filo>

<Passo numero={1} titolo="I concetti che servono prima">

### Cos'è un JWT

Un **JWT** (JSON Web Token) è un «lasciapassare» che i siti danno dopo il login, al posto di tenere una sessione lato server. È una stringa in tre parti separate da punti: `header.payload.firma`.

- **header** — dice come è firmato il token (es. algoritmo `HS256`)
- **payload** — i dati (es. `{"isadmin": false}`)
- **firma** — un «sigillo» calcolato con una chiave segreta, che dovrebbe impedire di modificarlo

L'idea: se cambi il payload, la firma non torna più → il server rifiuta. **A meno che** tu non riesca a conoscere o controllare la chiave di firma. Ed è qui che nasce il bug.

### HS256 e il punto debole

`HS256` è un algoritmo **simmetrico**: la *stessa* chiave serve sia per firmare sia per verificare. Conseguenza fondamentale: **se conosci la chiave, puoi forgiare token validi a piacere.** Normalmente la chiave è un segreto sul server. Ma se riesci a far usare al server una chiave che *tu* conosci... hai vinto.

### Cos'è il path traversal

**Path traversal** = far leggere al programma un file diverso da quello previsto, infilando `../` (sali di una cartella) nel percorso. Se il codice fa `apri("/cartella/" + nome)` e tu metti `nome = ../../../../etc/passwd`, finisci a leggere file fuori dalla cartella prevista. La radice del problema è sempre la stessa: **input dell'utente usato in un percorso file senza sanificazione.**

</Passo>

<Passo numero={3} titolo="Bug 1: kid path traversal → forgiare il token">

Il `kid` («key id») è un campo dell'header JWT che dice al server *quale chiave* usare per verificare la firma. Il codice vulnerabile:

```python
kid = header.get("kid")      # l'attaccante controlla questo
key = load_key(kid)          # apre f"/tmp/keys/{kid}.txt"
```

Vedi il problema? Il `kid` viene dall'header del token — **non verificato, controllato dall'attaccante** — e finisce dritto in un percorso file, senza sanificazione. È **path traversal** applicato alla scelta della chiave di firma.

### Il ragionamento (questo è l'oro)

Niente vieta che `kid` sia `../../../../qualche/file`. E qui scatta l'intuizione che lega i due concetti del passo 1:

1. HS256 è simmetrico → se controllo la chiave, forgio token validi.
2. Posso puntare `kid` a **un file di cui conosco/prevedo il contenuto**.
3. Quindi: punto `kid` a un file dal contenuto noto o vuoto → **conosco la chiave di firma** → firmo io stessa un token con `{"isadmin": true}` che verifica perfettamente.

Il trucco classico: puntare `kid` a un file **vuoto o prevedibile** (es. un README noto, o un path che dà contenuto vuoto). Se la chiave è «vuoto», firmo con chiave vuota. Il controllo `isadmin` è completamente aggirato.

<FraseChiave>La firma del JWT doveva garantire «questo token è autentico». Ma se l'attaccante sceglie con quale chiave lo verifichi, la firma non garantisce più niente. Non far mai scegliere al client la chiave di verifica.</FraseChiave>

</Passo>

<Passo numero={4} titolo="Bug 2: playlist abuse → lettura file locale">

Ora che sei admin, c'è una funzione che accetta una **playlist** (formato HLS/m3u8 — quello dello streaming video). Il codice valida il *nome* del file (una regex blocca il traversal sul filename), **ma non limita mai il `content`** della playlist.

### Il ragionamento

Una playlist m3u8 è un file di testo che elenca «segmenti» (pezzi di video) da caricare. Ma i segmenti si possono riferire a file locali con lo schema `file://`:

```
#EXTM3U
#EXTINF:10,
file:///etc/passwd
```

Il player risolve diligentemente la playlist, legge il «segmento» referenziato via `file://`, e il gestore ti restituisce il primo megabyte nella risposta. **Questo è un primitivo di lettura file locale arbitraria** — esattamente ciò che useresti per leggere un file sensibile, o per leggere `/tmp/keys/*` e rendere il Bug 1 ancora più facile.

<Flusso passi="La regex controlla il FILENAME (blocca il traversal lì), ma NON controlla il CONTENT, playlist malevola con file:///percorso/file/sensibile, il player legge il file locale → il contenuto torna nella risposta" evidenzia="ma NON controlla il CONTENT" />

> **Il difetto:** hanno protetto *una* via d'ingresso (il filename) ma ne hanno lasciata aperta un'altra (il contenuto). È lo stesso pattern dell'`X-Original-URL` (controlli una cosa, l'azione ne usa un'altra) e del parser differential: *la protezione guarda nel posto sbagliato.*

</Passo>

<Passo numero={5} titolo="La catena completa">

<Flusso passi="1. kid traversal → chiave nota, 2. forgio JWT isadmin:true, 3. da admin invio playlist malevola, 4. file:// legge il file che voglio, 5. il contenuto torna nella pagina" evidenzia="5. il contenuto torna nella pagina" />

Due bug che da soli sarebbero limitati (un file read senza privilegi, o un token forge senza niente da fare) **insieme** danno accesso completo ai file del server.

</Passo>

<Passo numero={6} titolo="Come difendersi">

- **JWT `kid`:** non usare mai un valore controllato dal client come percorso file. Il `kid` va validato contro una **lista chiusa** di chiavi conosciute (allowlist), mai concatenato in un path. E in generale: non far scegliere al client l'algoritmo o la chiave di verifica.
- **Playlist / file read:** validare **tutto** l'input, non solo il filename. Bloccare lo schema `file://` nei contenuti; limitare il player a schemi sicuri (solo `http`/`https` verso domini permessi). *Se validi solo una parte dell'input, l'altra è la falla.*
- **Principio generale:** quando proteggi un input, chiediti *«quali altri modi ha questo dato di influenzare il sistema?»* — il filename era protetto, il contenuto no.

</Passo>

## Cosa portarti dietro (il metodo)

<LatoHacker importante>
1. **I bug gravi sono catene.** Un file-read + un token-forge, da soli, sono mezze cose. Insieme = compromissione. Il hunter vede le connessioni.
2. **Input in un percorso file = sospetto immediato.** Ogni volta che un valore controllato dall'utente finisce in `open()`, `load()`, un path → pensa path traversal.
3. **«Hanno validato il filename ma non il contenuto.»** La protezione parziale è il nemico: cerca sempre la via d'ingresso che il controllo *non* copre.
4. **Il filo di sempre:** il sistema si fida di qualcosa che il client controlla (il `kid`, il contenuto della playlist). *Se lo scrivi tu, non è una prova.* — lo stesso principio della lezione [Authentication](/lezioni/02-vulnerabilita-web/02-autenticazione).
</LatoHacker>
