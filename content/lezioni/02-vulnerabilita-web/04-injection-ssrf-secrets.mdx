## Il filo rosso: SOURCE → SINK

<Filo>Una vulnerabilità è reale solo se l'input arriva al sink E niente nel mezzo lo neutralizza.</Filo>

<SourceSink
  source="form / URL / header"
  sink="operazione pericolosa"
  guardia="un sanitizer"
  sicuro="C'è una guardia tra source e sink (parametrizzazione, allowlist): il taint si interrompe, l'input resta un dato."
  vulnerabile="L'input attraversa l'app e raggiunge l'operazione pericolosa senza che niente lo neutralizzi."
/>

- **Source** = dove l'input entra (form, URL, header, file).
- **Sink** = l'operazione pericolosa dove il dato «detona» (query, richiesta HTTP, comando).
- Le tre vulnerabilità qui sotto sono tre istanze della stessa idea.

<Passo numero={1} titolo="Injection (SQL / NoSQL)">

**Il concetto in una frase:** il tuo input **smette di essere un dato e diventa un'istruzione**, perché l'hai mischiato nella stessa stringa del comando. Il motore non distingue più «cosa cercare» da «cosa fare».

```
input:    ' OR '1'='1
l'app concatena:   SELECT * FROM users WHERE name = ' + input + '
risultato:         ...WHERE name = '' OR '1'='1'
→ '1'='1' è SEMPRE vero → ritorna TUTTE le righe → auth bypass
```

L'apice `'` dell'attaccante **chiude** la tua stringa. Tutto ciò che viene dopo non è più un nome: è **logica di query** che il motore esegue.

<SourceSink
  source="campo username / password"
  sink="query SQL al database"
  guardia="query parametrizzata"
  sicuro="Il dato viaggia separato dal comando (name = ?): resta un VALORE, non può diventare sintassi."
  vulnerabile="L'input è concatenato nella stringa della query: diventa SINTASSI e cambia ciò che la query fa."
/>

### NoSQL è la stessa idea, forma diversa

MongoDB non interpreta SQL — ma l'input può diventare **logica di query** se arriva a un **filtro** come oggetto invece che come valore.

```
db.users.find({ "user": input_user, "pass": input_pass })
input malevolo:  pass = { "$ne": null }   → "password diversa da niente" → combacia con tutti
```

Il pericolo sono gli **operatori** (`$ne`, `$gt`, `$where`) dentro un filtro di `find()`/`update()`.

> **Punto chiave:** l'injection NoSQL vive nei **filtri di query**. Un `insert_one()` che scrive un documento con chiavi fisse e input solo come *valori* NON valuta logica di query → i valori sono salvati come dati, non eseguiti.

### Come si prova (ottica attaccante)

<LatoHacker>
- Lancia un singolo apice `'` su ogni campo. Errore 500 o messaggio SQL = la stringa si è rotta = iniettabile.
- `' OR '1'='1` sui login per rendere il `WHERE` sempre vero.
- **Blind time-based:** un payload che forza un ritardo (`WAITFOR DELAY`). Se la pagina si blocca 5 secondi, controllo la query anche senza vederne l'output.
- NoSQL: invia `{"$ne": null}` o `{"$gt": ""}` dove ci si aspetta una stringa.
</LatoHacker>

### Dove vive (il sink) e cosa lo uccide

Qualsiasi chiamata al DB dove l'input è **concatenato**. **Sink sicuro:** l'input entra solo come *valore* (parametro bound, o valore di campo in un insert).

- **Query parametrizzate / prepared statement** — il fix numero 1. Il dato viaggia *separato* dal comando, non può mai diventare sintassi.
- NoSQL: valida i tipi, forza le stringhe, rifiuta i dizionari.

<FraseChiave>Se l'input può cambiare ciò che la query FA, non solo ciò che CERCA, è iniettabile.</FraseChiave>

</Passo>

<Passo numero={2} titolo="SSRF — Server-Side Request Forgery">

**Il concetto in una frase:** costringi **il server** a fare una richiesta *al posto tuo*. Ora bussi dall'**interno** della rete — oltre il firewall, con i privilegi del server.

<Schema titolo="Dove punta il server, se controlli tu la URL">
- `169.254.169.254` → metadata cloud (AWS/Azure/GCP) → **credenziali temporanee** dell'istanza
- `10.0.0.5:8080` → admin panel interno, non esposto a internet
- `localhost:6379` → redis / db senza autenticazione
</Schema>

L'obiettivo più ambito è l'endpoint dei **metadati cloud** `169.254.169.254`: restituisce credenziali temporanee. Da lì l'attaccante si muove nel cloud.

### La domanda che decide tutto: l'attaccante controlla l'HOST?

```
url = user_input                        → SSRF REALE (possiede l'host)
url = "https://api.fidato.com/" + path  → vincolato (solo path, host fisso)
url = "https://fidato.com/?q=" + enc(x) → NON sfruttabile (host fisso + guardia)
```

Se l'host è fisso e validato, l'input finisce solo nella query string — e **non è SSRF**, perché la destinazione non cambia.

### Come si prova + il sacchetto dei bypass

<LatoHacker>
- Ogni campo che accetta una URL è un candidato: webhook, «importa da link», avatar-da-URL, «genera PDF da URL».
- Puntalo a un server che controllo → se ricevo la chiamata, il server fa richieste che dirigo io. Poi pivot verso l'interno.
- Blocchi «localhost»? Provo `127.0.0.1`, `0.0.0.0`, `[::1]`, o l'IP in decimale.
- **Redirect:** la mia URL passa il controllo, poi fa un 302 verso l'IP interno.
- **DNS rebinding:** l'hostname risolve «sicuro» al controllo, «interno» alla richiesta.
</LatoHacker>

### Cosa lo uccide

- **Allowlist** di host + scheme: rifiuta tutto ciò che non è *esattamente* consentito — e ricontrolla *dopo* la risoluzione DNS.
- Non far mai fornire all'utente scheme + host; solo un path vincolato su una base hardcoded.
- Blocca i range privati; disabilita il following dei redirect.

<FraseChiave>L'SSRF riguarda la DESTINAZIONE. Se non posso spostare l'host, non posso forgiare la richiesta — qualunque cosa metta nella query string.</FraseChiave>

</Passo>

<Passo numero={3} titolo="Hardcoded secrets (password/chiavi nel codice)">

**Il concetto in una frase:** una password scritta nel sorgente non è nascosta — è **pubblicata**. E Git la ricorda *per sempre*, anche dopo che cancelli la riga.

<Schema titolo="Dove finisce un segreto scritto nel codice">
- la **git history** (per sempre, anche dopo la delete)
- ogni **fork** e **clone**
- i **log** di CI / i backup
- i **laptop** di ogni dev
</Schema>

- Una connection string di produzione trapelata = lettura/scrittura diretta sui dati. Nessuna catena di exploit necessaria.
- Difficile da ruotare → nessuno lo fa → lo stesso segreto vive per anni.
- **Raggio d'impatto:** copiato in fork, log, backup, CI che non controlli.

### Caso speciale: la chiave di firma delle sessioni

Una chiave che **firma i cookie di sessione** (es. `SECRET_KEY` in Flask) è ancora più critica: chi la conosce può **forgiare sessioni valide** — fabbricarsi un cookie «sono l'admin» che l'app accetta come autentico. È game over per l'autenticazione (collega questo a [Authentication](/lezioni/02-vulnerabilita-web/02-autenticazione): «se lo scrivi tu, non è una prova» — qui l'attaccante *diventa* chi firma). Ruotarla invalida tutte le sessioni attive.

### Come si cercano (ottica attaccante)

<LatoHacker>
- Clona il repo e fai grep di **tutta la history** (con tool come `trufflehog`, `gitleaks`).
- Cerca su GitHub pubblico pattern come `mongodb://`, `password=`, chiavi API.
- Un segreto cancellato è ancora in `git log` → **cancellare ≠ rimuovere**.
- Dove vive: file di config, `Dockerfile`, YAML di CI, messaggi di commit, fixture di test, e vecchi valori **commentati** — gli scanner leggono anche i commenti.
</LatoHacker>

### Cosa lo uccide

<Flusso passi="Secret store (Vault / K8s Secret) — l'unica copia reale, iniettato a runtime come variabile d'ambiente, il codice legge un RIFERIMENTO (os.environ) mai il valore" />

- Il segreto vive in un **Secret store** → iniettato come env var → il codice legge `os.environ`. Il valore non è mai nel sorgente.
- **Ruota** qualunque segreto abbia mai toccato il repo — trattalo come compromesso. Spostarlo è *cleanup*; la rotazione lo neutralizza davvero.
- `.gitignore` + scanner di segreti pre-commit, così non rientra più.

<FraseChiave>Non puoi de-pubblicare un segreto. La rotazione è il fix; spostarlo fuori dal codice è solo pulizia.</FraseChiave>

</Passo>

<Passo numero={4} titolo="La domanda dietro tutte e tre">

Quando valuti una segnalazione, non chiederti «fa paura?» — chiediti la domanda specifica che decide il caso:

| Vulnerabilità | La domanda che decide | Sicuro se… |
|---|---|---|
| **Injection** | l'input diventa *logica* di query o resta *valore*? | resta valore (parametro / valore di campo) |
| **SSRF** | l'attaccante può controllare l'*host*? | host fisso e validato |
| **Secret hardcoded** | il valore ha mai toccato il repo? | mai nel repo (Secret store + rotazione) |

> **Il principio unico — SOURCE → SINK.** Ognuna è la stessa forma: input non attendibile (source) attraversa l'app e raggiunge un'operazione pericolosa (sink). È reale solo se l'input arriva al sink *e* niente in mezzo lo neutralizza. Gli scanner automatici (SAST) **vedono il flusso** ma spesso **non vedono la protezione in mezzo** → falsi positivi. Il giudizio umano verifica *cosa c'è tra source e sink*.

</Passo>

## Glossario rapido

<Callout tipo="nota" titolo="Le parole che useremo">
- **Taint (dato «sporco»):** input non attendibile di cui si tiene traccia mentre attraversa il codice.
- **Sanitizer:** operazione che «pulisce» il dato e interrompe il taint (parametrizzazione, allowlist).
- **Source:** punto d'ingresso dell'input non attendibile.
- **Sink:** operazione pericolosa dove il dato può causare danno.
- **Allowlist:** elenco chiuso di valori permessi; tutto il resto è rifiutato (più sicuro di una blocklist).
- **Rotazione:** sostituire un segreto con uno nuovo, rendendo inutile quello vecchio esposto.
</Callout>

<Domande titolo="Domande da farti davanti a un input">
- Dov'è il **source** e dov'è il **sink**? Cosa c'è **in mezzo**?
- In una query: l'input resta un **valore** o può diventare **sintassi**?
- In una URL fornita dall'utente: posso spostare l'**host**, o solo il path/la query?
- Questo segreto ha **mai toccato** il repo? È stato **ruotato**, o solo spostato?
- C'è davvero una **guardia** tra source e sink, o lo scanner ha segnalato un flusso già protetto?
</Domande>
